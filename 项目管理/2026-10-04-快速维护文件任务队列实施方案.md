# 快速维护文件任务队列实施方案

- 日期：2026-10-04
- 状态：用户以“执行吧”批准底层改动；1.4.25 本地实施、双引擎定向验收及资源整理完成。GitHub CI 与正式安装包待用户执行。
- 目标：优先解决大批量资料同步的卡住、误取消、重复执行和进度不可见；保留快速维护五步入口，为关联与索引的小批次续跑复用任务机制。

## 1. 实施前调查证据

1. 工作区产品版本为 1.4.24，Git 工作区调查开始时无未提交修改。当前运行进程来自 `D:\Program Files\PMBrain`；该目录 `resources/release-manifest.json` 标记 1.4.21。已运行安装版不能作为 1.4.24 修复的验收对象。
2. `src/product/tasks/task-worker.ts` 的 `runDreamTask` 按 Source 顺序调用 `runQuickMaintenance`，每个 Source 的所有阶段仍在一个产品任务 Worker 内执行。
3. `src/product/tasks/runtime.ts` 的默认任务超时已为 6 小时。重启将遗留 active 产品任务标为 paused；执行器拒绝再次自动执行已启动过的任务。普通导入重试带 `resumeCheckpointId`；快速维护重试重新提交 Dream，没有文件队列恢复合同。
4. 同步并非没有增量或断点：已有 Git diff、内容 hash、`sync-full` 操作检查点和失败门禁。`src/commands/sync.ts` 的 `performFullSync` 调用 `runImport` 时传入了操作检查点，但没有传入现有 `runtime.signal/beforeFile/onFile`，文件级取消和完成回执没有接完整。
5. `src/core/import-file.ts` 已在事务前完成主要解析和 Embedding，按页面事务写入；不能把本次修复描述成首次将全部模型调用移出事务。单页面的正文、分块、标签和关联写入仍可能占用很长事务，文件任务拆分本身不会消除超大单文件写入延迟。
6. `src/product/database/database-worker.ts` 已有 PGLite 独立唯一 owner 和请求优先级调度。复用该写入入口，不再创建第二个 PGLite Writer。
7. `minion_jobs` 已有 `parent_job_id`、`waiting-children` 和父任务收敛基础，但现有产品任务启动、停止、重试策略尚未适配这条链路。父任务不能占住 Worker 等待子任务，也不能被按普通整轮任务重复执行。

## 3. 拟实施范围

### A. 扫描与文件任务

- 保留检查、同步、关联、搜索索引、完成检查五项产品步骤及既有阶段顺序。
- 父任务负责 Source 扫描、任务创建、阶段推进和汇总；扫描及任务入队也分页执行，不一次写几千行的长事务。
- 为真正需要处理的文件生成持久化子任务，复用 `minion_jobs`；任务标识至少包含 brain/Source、相对路径、文件内容指纹、Git 基线（适用时）、解析规则版本。
- 复用现有增量判断，mtime/size 只作便宜的候选过滤，不作为唯一内容正确性依据。普通目录仍不执行 Git；Git 源仍遵守“是否包含未提交内容”的现有设置。
- 文件任务不能依赖上一进程已经删除的临时 Git 快照路径。重启后按记录的提交重建快照并验证内容；本地文件变化后只重新安排变化文件。
- 每个文件提交成功后立即确认持久化结果；提交成功、回执尚未写入就崩溃时，恢复通过实际内容/版本确认结果，避免重复写版本或重复调用模型。

### B. 解析与写入

- 复用现有解析、OCR、分块、模型、Embedding 入口；有限并发准备，写库复用唯一数据库 Worker，禁止无限创建线程或积压完整大文件。
- 常规文件按现有页面原子提交。写入前后校验 Source、文件版本、页面版本、模型配置、租约令牌和停止状态。
- 同步先持久化正文和分块，向量交给既有后续阶段补齐；这是明确的执行顺序变化，需要在代码及结果合同中区分“资料已同步”和“向量待补”，保留原错误原因和旧向量的模型归属。
- 对超大单文件先在隔离夹具测量事务热点。若需要分批安装分块，必须采用暂存完整新版本后原子发布的方案，不能分批删除/覆盖当前可见分块，暴露半份文件。涉及新 Schema 或数据布局时另行确认具体设计；不得以拆文件任务宣称单文件事务已变短。

### C. 失败、停止与恢复

- 文件解析等单文件错误只影响该文件，其余正常文件继续；仅已尝试并失败的文件计入失败数。未领取文件显示未处理，不批量写成“任务已取消”。
- 数据库断连、索引损坏、Source 不可用、令牌失效等基础设施错误暂停相关执行并显示原生原因，禁止将其当文件错误反复重试。
- 可恢复的临时错误按文件有限重试并退避；确定性解析错误、认证错误和未明确可安全重放的付费请求不无条件重试三次。
- 停止先阻止领取新文件，再通知当前 Worker，在安全边界退出；所有旧执行者实际退出前不允许重领。已提交结果保留，尚未开始文件仍可后续继续。
- 重启恢复已持久化的待处理文件；先确认旧 owner 已退出，并核对实际页面、指纹与模型状态。用户显式停止的任务不在重启后自行启动；付费模型结果不确定的任务保留待确认状态。
- 父任务通过现有等待子任务机制释放执行槽；子任务终态后由父任务重新汇总、推进下一阶段，不从第一步重跑。
- 部分失败保留部分完成结果与可继续入口；只有满足原有同步失败门禁才推进 Source bookmark，未完成不能提前推进。只在权威扫描完成后按原规则处理软删除及重命名，不删除原始资料。

### D. 进度与后续复用

- 同步详情显示真实的扫描数、未变化数、待同步数、已完成数、失败数、未处理数和当前文件；文件完成含“已确认提交”，不把排队当完成。
- 刷新及重启后可读历史汇总与文件结果；父任务用于普通列表，文件详情分页读取，避免几千条子任务淹没任务中心或放进同一个巨大 progress JSON。
- 本轮将同步完整接入。关联、索引继续复用原业务逻辑及现有批次，提供相同的任务/检查点适配边界；未完成双引擎与行为验收前，不宣称后两阶段已改成独立可恢复队列。

## 4. 先写的验收脚本

用产品行为描述验收，全部使用临时 Source、合成文件和隔离数据库：

1. 准备数千个文件，先同步一部分，再继续；已成功文件不重复落库，显示当前文件与真实计数。
2. 文件完全不变时再次维护；不重新解析/OCR/调用向量模型。只修改一个文件，仅安排该文件及确有需要的派生更新。
3. 中间加入两个坏文件；它们独立失败，之后的正常文件仍完成，剩余数与失败数准确。
4. 同步中停止；未开始的文件不报失败，旧 Worker 退出后才可继续，停止后没有迟到提交。
5. 在“文件提交后、确认记录前”及“确认后”分别结束隔离进程，再重启；完成结果保留，不重复版本，继续未完成文件。
6. 使用跨越旧 25 秒门槛的受控写入验证续锁，另测真实大文件；等待模型期间无写事务，文件间允许交互读取，令牌真的被替换则禁止提交。
7. 验证父任务等待子任务时不占满全部执行槽；部分失败也能正确收敛，不永远停在 waiting-children。
8. 两个 Source 有同名路径时不串库；分别验证 Git 已提交、包含未提交内容、普通非 Git 目录、删除与重命名。
9. 临时文件在恢复前改变、页面被其他入口改动、模型配置改变、数据库断开时分别显示真实原因，不覆盖更新结果。
10. 正文同步后可以关键词检索；向量失败只显示待补或失败，修复后补齐，不重复导入正文。

涉及数据库合同的用例在 PGLite 和独立 Postgres 测试库运行。前端改动用当前工作区源码和最新 Desktop 资源验收，覆盖入口、运行、停止、继续、失败、刷新、重启及真实进度。按范围执行定向测试及类型检查，不自动跑本地全量测试。

## 6. 与贴入建议的明确差异

- 增量判断、事务外准备、操作检查点和单 Writer 已有基础，采用复用与补齐，不重复建设。
- 不对所有错误机械重试三次，不自动重放结果不确定的付费调用。
- 重启自动恢复待处理工作，但用户停止状态和不确定的模型调用保留。
- 本轮以同步完整链路为交付范围；关联与索引预留复用机制，进一步独立队列化另做行为验收。
- 超大文件事务分批不能牺牲页面原子性；如必须新增暂存 Schema，具体设计另行确认。

## 7. 实际实施结果与验收

- 快速维护保留五步及普通导入/CLI 原路径，增加可选文件执行适配器；复用 `minion_jobs`，未增加数据库表。父任务扫描后释放执行槽，文件 Worker 有限并发执行；子任务终态后从阶段检查点汇总继续。
- SHA256、Source、实际目录、解析规则及模型配置组成任务指纹；不变文件经实际页面内容确认后跳过。文件提交回执与页面更新在同一事务中持久化，恢复先核对实际页面，避免重复版本。Git 临时快照内容复制到 brain 专属任务暂存目录并校验，原资料不变。
- 单文件解析错误独立收敛；基础设施错误暂停并保留原因。停止和继续沿用同一会话，已完成结果保留；显式停止不会在重启后自动启动，安全待处理文件可恢复，不确定模型请求暂停供用户继续。
- 新增真实扫描/未变化/已完成/失败/未处理计数、每页 50 条文件结果与继续入口；普通任务列表隐藏内部文件任务。关联、搜索索引与完成检查复用既有核心能力，保存阶段结果，保留模型及向量错误反馈。
- 文件事务在提交前核对原文件、Source、页面、模型和租约；本进程持有写事务时不因续锁排队超时而误取消。令牌失效、用户停止及原资料变化仍阻止提交。完成的暂存副本仅在严格目录边界内清理。

### 与原实施规划的差异及剩余边界

1. 文件入队按单文件短事务进行，缓存读取上限 5000 行并有逐项查询回退；原生目录发现仍收集路径列表，未实现完整分页发现。实测规模为 1000 文件，未宣称数千文件已验收。
2. Git 恢复采用持久化、校验过的内容副本，不在每次重启重建 Git worktree；任务键用实际字节 SHA256 与目录归属保持已提交/未提交内容隔离。
3. 未新增分块暂存 Schema 或分批发布页面；保留原子页面事务，减少重复校验。单条长 SQL 仍可能阻塞必须读库的页面，27 秒测试只证明不会因此误取消，不能证明所有超大文件很快。
4. 保留核心现有有限重试；未添加任务层对基础设施或结果不确定付费请求的自动重放，改为保留原错误并暂停，用户可明确继续。
5. 关联和索引仅接入阶段检查点、续跑适配边界，未独立文件队列化；商业 OCR/模型语义与真实用户资料尚未验收。1000 文件使用合成 Markdown，不能等同于 1000 个扫描 PDF 的耗时。
6. 旧任务中已保存的取消/退出错误不会清空。现有安装资源仍是 1.4.21，本次未停止生产进程、提交、推送、执行远端 CI 或 `bun run build:win`。只有用户打包安装后，旧安装版才获得修复；远端精确 SHA 的 CI 尚未完成。

### 推荐的一体实施范围

1. 控制与执行分离：PGLite 保持一个所有者、一套 BrainEngine 和一个数据库目录，把所有者移到独立可结束的子进程；不增加第二个打开同目录的实例。正常停止在操作边界回滚；执行进程因同步 WASM 无法响应停止时，由外部控制器结束该执行进程，等待退出后按原生打开流程恢复并核对回执。不得直接杀整个桌面软件，不自动重建库或重置 WAL。如果打开或数据校验失败，明确停在“数据库恢复失败”，保留数据与错误，不能冒充已安全恢复。
2. 停止意图在既有 task-artifacts 中先持久保存，先拒绝新文件与新 RPC，再发停止信号；安全回滚/退出和取消落盘完成才显示“已停止”。恢复重启仍尊重停止意图，模型结果不确定的请求不自动重放。一次数据库所有者恢复会影响正在等待同一数据库的操作，需明确暂停这些操作并保留错误。
3. 文件明细为执行记录的只读投影：沿用任务 ID、Source 和分页边界，在扫描入队、开始、实际回执、独立失败时维护快照；运行中查看不等待正在写库的 SQL。显示更新时间和停止/恢复状态，未知结果不标成完成。数据库可用时与权威 minion_jobs 回执核对；不得新增一套导入业务逻辑或编造文件结果。
4. 真实大文件进度：显示并行执行文件的名称、Source、KB/MB、读取/解析/切分/正文写入/生成向量/向量写入/完成；正文每批实际完成数，向量已生成/已写入/复用/待处理数，正在等待的数据库操作及持续时间。未启用向量时明确显示“本轮未启用向量化”。长时间无新批次结果只显示当前等待，不能虚构连续进度。继续沿用已有大文件和向量路径，不以删除索引或牺牲页面原子性换取快进。

### 实施前探针及必须通过的验收

- 隔离合成库探针已执行：独立 owner 提交一份页面及分块后，在另一未提交页面事务内执行无限 SQL；外部结束 owner 约 389ms，原生重开后已提交页面/分块存在、未提交页面不存在。该结果仅证明这一隔离场景可行，不等于真实旧库/所有故障均安全恢复。探针在忽略目录 `.codex/sync-stall/stop-owner-probe.ts`，日志在系统临时目录 `pmbrain-stop-owner-probe.log`。
- 先写可执行验收脚本，再实施：普通解析中停止、模型等待中停止、长 SQL 中停止、模拟同步 WASM 不返回时停止；文件明细始终快速返回；全部使用隔离资料，不停止生产进程。
- 在真实备份副本验证 owner 异常结束后的旧页面、版本、Source、分块及向量摘要不变，新事务未提交内容不可见，已提交文件回执可恢复；禁止使用 resetwal 或清空数据库让测试通过。

- 两种数据库覆盖停止后刷新/重开、同会话继续、不确定模型调用暂停、完成回执防重复、另一个 Source 同名文件及取消状态不会回退。Postgres 沿用现有连接取消能力，不给它复制 PGLite 子进程逻辑。
