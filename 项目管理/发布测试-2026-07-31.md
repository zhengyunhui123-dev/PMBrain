## 二、对你四点判断的验证结论

### 1. 「新用户 + postgres，没坑」→ ❌ 有坑（仅限 CLI init 路径）

走 `init --url ... --embedding-model ollama:qwen3-embedding:0.6b --embedding-dimensions 1024`：

- 保存到 config.json 的却是 **768**（recipe 推导值覆盖了用户显式传入的 1024）
- schema 按 768 建列，import 时 ollama 实际返回 1024 → **3/3 全部报 `Embedding dim mismatch`，无法导入**
- 终端还显示 `AI Gateway (mimo) 已配置 — embedding: mimo:mimo-embedding (1024d)`，与实际保存的模型也不一致

**但桌面端路径（先写 config.json 再跑迁移）完全正常**：schema 113 + vector(1024) + 配置一致。即：桌面端新用户没坑，CLI 新用户必踩。

### 2. 「老用户 + postgres，没坑」→ ✅ 实测没坑

副本从 version 100 迁移：13 个迁移全部成功到 113，迁移前后 5199 页 / 26121 向量完全一致，搜索与语义查询正常召回真实笔记。

### 3. 「新用户 + PGlite，向量化不能超过4000维度要设置，只能单线程」→ ✅ 符合预期

- 4096 维初始化时 v45/v55 迁移输出警告并继续：`HALFVEC(4096) exceeds the 4000-dimension HNSW limit; keeping full-width ... with exact search.`（77a0f74 修复生效，不再中断迁移）
- 列保留全宽 `vector(4096)` / `halfvec(4096)`，HNSW 索引正确跳过，走精确扫描
- 单线程实测：`autoConcurrency('pglite') = 1`，`resolveWorkersWithClamp(pglite, override=8) → workers=1`

### 4. 「老用户 + PGlite 迁移失败 = 迁移时数据库被锁」→ ✅ 实锤，但机制比预想的多一层

**锁竞争实验（复现你的场景）**：

| 实验 | 结果 |
|---|---|
| A 进程（serve）持有 brain.pglite 锁，B 进程跑迁移 | **B 等待 33 秒后失败**：`GBrain: Timed out waiting for PGLite lock.` |
| A 被杀后锁目录残留，B 重试 | ✅ stale 检测（PID 死亡判定）自动清锁，迁移成功到 113，数据完好 |
| A 活着时手动删除锁目录，再跑 B | B「成功」——但 A、B 两个 WASM 实例同时写同一数据目录（本次未造成可见损坏，属高危操作） |

结论链：

1. **迁移失败的直接原因就是锁**：桌面 sidecar 常驻持有 brain.pglite，升级触发的迁移进程 30 秒拿不到锁就失败。
2. 「锁无法移除」不完全准确：**死进程的残留锁能被 stale 检测自动清理**（实测 406ms 完成清理+连接），不需要手动删。
3. 真正的风险是：**活进程持锁时按错误提示手动删锁** → 双进程写库。错误提示文案会引导用户这么做，需要改。
4. 根治方向：升级/迁移流程必须先确保 sidecar 退出（检测 PID 并等待/请求退出），而不是让用户手动处理锁。

## 三、问题清单（按优先级）

### P0-1 CLI `init --url` 维度/模型解析不一致（新用户必踩）

- 现象：显式传 `--embedding-dimensions 1024`，保存 config 与建 schema 都用 768；import 全部失败
- 影响：任何按文档用 CLI 初始化 + ollama 本地模型的新用户
- 绕行：桌面端路径无此问题
- 涉及：`src/commands/init.ts`（initPostgres 分支 resolvedDim/resolvedModel 链）、ollama recipe default_dims=768

### P1-1 PGlite 迁移与 sidecar 锁竞争（老用户升级必踩）

- 现象：sidecar 常驻时升级迁移 30 秒超时失败
- 修复方向：桌面端升级流程先检测并退出 sidecar 再迁移；锁超时错误文案不应引导手动删锁（或必须强调先结束进程）
- 涉及：`src/core/pglite-lock.ts`、桌面端升级流程、`apply-migrations`/`init --migrate-only` 入口

### P1-2 活进程持锁时手动删锁 → 双进程写库风险

- 锁超时错误信息建议用户 `remove .gbrain-lock`，照做后会产生两个 WASM 实例写同一数据目录
- 建议：错误文案改为「请先退出正在运行的 PMBrain（含桌面端托盘），再重试」，不提示手动删锁

### P2-1 query 在 chat/expansion 模型不可用时卡死

- ollama:qwen3.6:latest（23GB）未加载时，query 无报错无结果，最终 `engine.disconnect() did not return within 10000ms — force-exiting`
- 建议：查询扩展加超时/降级（跳过扩展直接语义检索）

## 六、修复规划（2026-07-31 定，未实施）

### 修复 1：P1-2 锁超时文案误导（先做，5 分钟，零风险）

- 文件：`src/core/pglite-lock.ts`（约 112-121 行的超时错误信息）
- 现状：提示 `If that process is dead, remove .gbrain-lock and try again`，引导用户手动删锁 → 双进程写库风险
- 改为：先报持有者 PID 与命令行，引导「请先退出正在运行的 PMBrain（含桌面端托盘）再重试」；手动删锁仅作为最后手段并明确警告
- 验证：`bun test test/pglite-lock.test.ts`

### 修复 2：P0 CLI init --url 维度解析（新用户必踩）

- 目标：用户显式传入的 `--embedding-model` + `--embedding-dimensions` 在三个环节保持一致——保存的 config.json、gateway 运行时、schema 建列
- 步骤：
  1. 先写失败测试：模拟 `init --url ... --embedding-model ollama:qwen3-embedding:0.6b --embedding-dimensions 1024`，断言保存的 config 为 1024 且 schema 为 vector(1024)（用产品经理语言：新用户指定了 1024 维模型，装完后导入不应报维度不匹配）
  2. 定位丢失环节：`parseArgs → aiOpts → resolveSchemaEmbeddingDim preflight → saveConfig` 链路上 1024 在哪一步变成 768（重点看 init.ts initPostgres 分支 resolvedDim/resolvedModel 的取值与保存时的拼接，以及为何终端显示 mimo 模型）
  3. 最小修复：只在参数链断点处修，不改 recipe/gateway 核心
- 验证：新测试通过 + `test/init-*.test.ts` 相关既有测试不回归 + 实测 CLI init --url 全流程（导入 3 文件无维度错误）
- 边界：这是 CLI 入口层修复，不动引擎/核心数据逻辑

### 修复 3：P1-1 桌面端升级迁移前先退 sidecar（老用户必踩）

- 目标：桌面端启动/升级流程中，跑迁移之前确保没有进程持有 brain.pglite 锁
- 方案：桌面端主进程在迁移步骤前读取 `.gbrain-lock/lock` 的 PID：
  - 若是本 Electron 实例启动的 sidecar 子进程 → 先正常 stop 再迁移
  - 若是其他 PMBrain 进程 → 弹窗提示「检测到 PMBrain 正在运行，请先退出后重试」，提供重试按钮，不擅自 kill
  - 若 PID 已死 → 直接继续（现有 stale 清理会处理）
- 修改面：`desktop/src/main/`（sidecar-manager / 启动编排），属于桌面端流程层，符合「桌面端调用 CLI 能力」原则，不需要 CLI 新增能力
- 验证：复现锁竞争场景（sidecar 常驻 + 触发迁移）→ 迁移不再 30s 超时失败

### 修复 4：P2 query 模型不可用时卡死（体验优化，最后做）

- 目标：查询扩展调 chat 模型失败/超时时不卡死

- 验证：模拟 chat 模型不可用 → query 有结果且耗时可控
