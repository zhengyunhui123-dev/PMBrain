# 知识整理分层与实体处理边界规划

日期：2026-10-19。修订方向：以原版 GBrain 为内核，收敛 PMBrain 额外实体编排。

状态：用户已确认执行，1.5.4 代码与本地隔离验收完成。正式知识库未运行维护，Postgres 环境、真实模型规模、远程 CI 和安装包验收仍待完成；不能称为完整发布验收通过。

用户当前原则：“延用 GBrain 的内核，人家怎么做照做就是”。上一轮提出的“快速维护轻、深度整理增加理解”继续作为产品体验目标，具体能力与执行链以查证的原版实现为准，不能先建另一套实体处理体系再称为沿用上游。

最初实现的作用，是将资料里的重要人物、公司、项目形成有来源的实体及关系。问题在于把完整摄入工作变成了资料同步后的自动维护环节，再持续补预算、凭据和恢复逻辑。不能只说“名称识别本来就要这么久”。不能由代码或提交作者推断每一步都由用户明确指定。

## 2. 原版 GBrain 实际如何分工

| 原版能力 | 作用与限制 | PMBrain 应如何复用 |
| --- | --- | --- |
| Dream 的 lint、backlinks、sync 等 | 检查、审计、同步 | 保持原有输入、顺序和真实结果，产品层展示中文名称 |
| extract / extract_facts | 提取已有链接、时间线或实体提及，或对账既有 Facts 结构 | 不把它们宣传成“对所有原文重新调用 AI 建实体档案” |
| synthesize | 对配置的会话/输入先筛选、缓存，再执行受配置和写入范围限制的综合 | 复用其原生适用输入、筛选、允许写入路径、断点和结果，不自行扩大到所有导入文档 |
| patterns、概念和其他知识阶段 | 按配置、Pack、输入与阶段依赖执行 | 不因界面叫“深度”就自动打开所有阶段 |
| embed / orphans 等 | 更新索引、审计缺少连接的知识 | 保留实际执行状态，分开显示模型、数据库和向量等待 |
| ingest / signal-detector Skills | 按用户明确请求或已启用的捕获范围，解析内容并创建或更新值得记录的对象 | 属于请求/Agent 能力和明确启用的捕获约定，不能等同于 Dream 对每篇资料的强制后台阶段 |

原版 Dream 的阶段表没有 capture_entities。本地原版 CLI 提供阶段选择，PMBrain 的“快速维护”是产品预设，不能称为原版存在完全同名、同范围的快速流程。

技术适配情况：capture_entities 复用了 Minion、Gateway、BrainEngine 和 runCycle 的挂接方式，所以能够接入；但它改变了默认要处理的材料和模型工作量，不能据此认定业务行为与原版等价。当前没有证据证明整个内核已被替换，也没有证据证明只剩 GUI 差异。

特别注意：原版 synthesize 的对象、输出和允许写入范围要逐项核对。不能把“有 synthesize”理解为“原版会为所有导入资料建好所有人名与项目页”，更不能直接把 capture_entities 改名为 synthesize 当成完成对齐。

## 3. 是否重构：先局部收敛，再按差异决定

当前建议是治理 Dream 与导入自动实体处理的局部业务接线，不先重写整个 Core、数据库或任务平台。

- UPSTREAM CORE：使用固定基线的原生阶段职责、算法、工具、预算解析、锁和失败规则；优先复用完整依赖链，而非复制零散函数。
- PMBrain ADAPTER：只保留多 Source、中文、国内模型、Desktop/PGLite 运行方式和旧用户兼容确实需要的适配，差异有清单和回归依据。
- PRODUCT：快速维护、深度整理、设置、结果和恢复的交互，不在产品页面另实现知识逻辑。

第一步是从默认快速维护和默认 Dream 的候选流程中撤出 PMBrain 额外的重型 capture 自动编排，具体代码变更在用户确认实施后执行。必须同时审查导入后请求、独立自动队列、重启恢复及调度入口，防止主流程不再调用，另一入口仍继续跑。

这不是立即删除所有 capture 文件或历史任务。先保留旧成果与历史读取、明确旧待续请求的去向，再确定哪些兼容代码可退役。原版已有的实体能力照原版复用；原版没有覆盖的产品要求列为明确缺口，不默认补出另一套后台 Agent。

上一版新增 basic/deep 实体协议、独立基础建档链和 roundId 调度的建议撤回。只有对照证明原版能力无法满足已确认的必要需求时，才单独提出最小适配及其成本，再由用户决定，不把扩展作为默认前提。

## 4. 两种产品入口的重新定位

| 入口 | 默认职责 | 实体的处理边界 |
| --- | --- | --- |
| 快速维护 | 同步新增变化、维护原有引用关系、按配置更新索引、报告异常 | 不默认对全部资料启动完整 ingest；原版已有的确定性提取和实体连接继续生效 |
| AI 深度整理 | 执行原版适用的理解、综合和知识整理阶段，遵守配置、筛选及原有启用范围 | 通过上游明确支持的综合/摄入路径形成实体与事实，不能强制再跑一遍独立全量实体 Agent |
| 用户明确要求保存、摄入或整理某份材料 | 调用原版对应 ingest/Agent 能力，保留来源及验收 | 可以生成重要人物、组织、项目等，但按原规则与授权范围执行 |
| 已明确开启的会话记忆或自动捕获 | 保留对应授权和原有作用域 | 不因退出 Dream 的额外 capture 阶段而一起关闭会话记忆，也不能借此扩大读取范围 |

关于上一轮“快速维护提取重要人名、项目”的要求：先核对原版在这些输入上的实际覆盖。若原版只能关联已有实体，不能把它描述成可以自动创建新人物或项目。若坚持给快速维护增加原版没有的轻量 AI 建档，那仍属于 PMBrain 新增能力，需要另行评审；本次优先遵从用户最新的上游内核原则，不立即实施这项扩展。

## 5. 时间设置：分清调度、超时和运行预算

| 概念 | 回答的问题 | 设置方式 |
| --- | --- | --- |
| 自动运行时间或频率 | 什么时候开始，例如每天某个时刻 | 沿用现有“设置 → 知识整理”的自动运行设置，保存并重载一致 |
| 单次模型请求超时 | 一次网络/模型请求多久未完成应停止等待 | 优先复用上游已有提供商或阶段配置；需要给用户调整时放设置的高级项 |
| 单项任务最长运行时间/预算 | 一项工作最多使用多久或多少预算 | 先核对上游已有配置和语义，必要时在设置中提供同一配置的入口，不另造重复预算系统 |
| 内部批次或调度分片 | 一次占用执行机会多久 | 内部实现细节，不作为普通用户必须理解或填写的“时间线”；是否保留由收敛后的真实链路决定 |

撤销上一版固定五分钟、二十分钟、请求次数、Token 配额和直接强制按轮切断的产品方案。不把五分钟配置成自动反复启动，更不能以轮换窗口掩盖没有完成的工作。

不要求用户为了正常使用先设置一堆时间。已有明确配置继续使用；未配置时优先按原版对应配置的默认语义运行，确有必要的 PMBrain 差异要说明理由后决定。配置读取优先级、单位、校验和保存均复用既有实现，不能 GUI 写一个值、后台仍用另一个写死值。

如果提供“最长运行时间”，至少验收设置保存、页面重载、任务派发、单次请求的剩余预算、超时取消与断点恢复；到达限制必须明确未完成范围。普通模型与向量模型保持独立配置，向量失败保留原生错误。不要把材料中的事件时间线和执行时间设置混为一谈。

原版 synthesize 已有 dream.triage.max_ms、dream.synthesize.subagent_timeout_ms、subagent_wait_timeout_ms、max_turns、cooldown_hours 等配置。它们分别表示筛选预算、请求/任务等待、轮数或冷却，不是整轮维护耗时承诺；不能把上游某个三十分钟超时当成用户过去三十分钟完成的原因。

## 6. 保留必要问题修复，避免全盘回退

| 项目 | 处理原则 |
| --- | --- |
| 1.5.2 线程退出和数据库恢复 | 保留已经验证的通用可靠性修复，不为回归原版撤掉 Windows 服务保护 |
| 1.5.3 事务回滚后的版本缓存 | 保留事务作用域内暂存、提交后生效的修复，真实外部修改仍阻止覆盖 |
| 完成凭据、增量向量复用 | 保留与实际输入、模型、Source 和事实绑定的有效成果，不重新向量化整个库 |
| capture 专用批量错误 | 退出默认流程后不再强迫普通维护不断付费修复；遗留的明确摄入入口仍须保留原错误，不能标假成功 |
| 历史实体、事实、关系和 Wiki | 全部保留，不删除、不重分类，不用回滚源码清理真实知识 |
| 数据库 upsertChunks 超时 | 单独定位排队、执行、批量和目标，不把减少实体工作当作 SQL 超时根因已修 |
| 副本与生成物 | 原文保存与搜索不受影响；遵循原生适用输入和排除规则，不因路径叫 output 就整目录丢弃 |
| 中文、国产模型、多 Source | 保留必要兼容和隔离；不能机械覆盖整个 src/core 或直接退回旧提交 |

用户反映过去经常约三十分钟完成、耗时主要在向量化，这是此次回归对照的重要体验输入。当前日志确认新增实体阶段成为额外耗时；向量阶段也要完整测量，不能仅把模型调用减少就宣称整轮恢复。

## 8. 实施顺序

1. 固定原版基线，对默认 Dream、快速预设、导入自动请求和旧任务恢复列出行为差异。
2. 制定最小代码变更，优先撤出默认重型 capture 编排，复用上游原生处理能力；列明因此暂缺的自动建档能力，不隐瞒差异。
3. 补齐设置的读取、保存和真实生效链路；仅暴露需要用户决定的调度或超时，不增加固定分轮平台。
4. 兼容旧任务和已有成果，不删除旧待续请求，不自动启动原本没有授权的全库摄入；待续范围、取消和继续必须清楚。
5. 在隔离副本和同一冻结材料上运行完整原生链路，检查阶段耗时、实体/关系质量、索引与服务恢复。
6. 同步现有变更/Bug 台账、GBrain 来源与成熟度记录及统一版本资源；本地验收、准确 SHA CI 和正式安装分别报告。提交和 build:win 仍由用户完成。

这属于对默认流程的定向收敛与必要适配，不预先承诺零架构改动。若对照后确需更换共享执行、持久结构或数据库 Schema，应先提交依赖、范围和兼容方案再确认，不能在“跟随原版”的名义下直接重写。

## 9. 验收边界

- 同一组材料、相同模型和向量配置、相同设备，对照原版适用链路与 PMBrain 的产品入口；输入范围不相同则明确列出，不能直接比较总耗时。
- 默认快速维护和默认 Dream 不再从导入、定时、重启恢复等旁路偷偷进入额外 capture Agent；明确摄入和已授权记忆能力仍按对应合同工作。
- 不变输入重复执行时，已完成且凭据有效的模型工作、重复事实和不变向量不重复计算；待续工作只继续剩余部分。
- 重要对象、事实和原文关系人工核对，原版不支持的自动建档明确为缺口，不伪造达成；不得为了模仿上游放弃 Source 和原始数据保护。
- 所有时间设置保存后重载一致，实际任务记录所用设置；到达已配置限制有明确结果，不会无期限反复识别或假成功。
- 分开记录同步、上游 AI 阶段、关系处理、数据库执行和向量化，核对用户所说过去约三十分钟的实际规模；不预先承诺固定三十分钟完成。
- PGLite 和 Postgres 验证事务、停止、重启、原任务继续及旧凭据兼容；源码 Admin/Desktop 验证入口、配置、结果、重载、失败反馈。
- 真实提供商、完整索引和正式安装未验收时，不以单元测试或 dry-run 认定真实问题全部修复。

## 9. 1.5.4 实施回执

- 默认入口：普通导入不再写入实体待续请求或派生完整实体任务；默认 Dream 和快速维护不含 capture_entities。运行器启动、文件完成和任务完成都不再自动补建该阶段；原版适用的提取、关系、向量阶段保留。
- 旧用户：旧独立自动实体任务暂停，不删除任务、待续请求、实体或关系。继续旧默认维护时，在原任务 retiredCapture 检查点中保存旧实体阶段、窗口和报告；保留已完成常规阶段、文件和原 ID。显式摄入仍可执行、停止和继续；部分完成的显式任务也能原 ID 继续，费用不重置。
- 时间：设置 → 自动化提供“整理任务单次执行上限（分钟）”。dream.task_timeout_ms 持久保存；显式任务参数优先，其次保存值，再次既有六小时产品默认。自动快速维护不再用固定两小时覆盖设置。已证实两秒测试上限能取消在途模型请求，数据库可查询、原文保留，同 ID 重试保留原上限。
- 验证：默认及快速预设 33 项通过；运行器与恢复 30 项通过、3 项 Postgres 跳过；实体/关系兼容 55 项通过；补充实际超时测试 5 项通过。本地 verify 40 项及 CI 预演 236 项通过；最新源码 Admin、Desktop、Sidecar 构建完成，打包资源的 Bun、Canvas、PGLite 检查通过。最新编译 Sidecar 页面测试：保存七分钟、刷新保留、旧客户端保存保值、五种非法值拒绝、清空恢复默认、快速维护完成、无页面 JS 错误。
